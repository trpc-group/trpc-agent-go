    Callbacks

    An agent run moves through a small set of recurring boundaries: entering and leaving an agent, calling an LLM, executing tools, and (when using AG-UI) translating events. Production applications often need cross-cutting behavior at these boundaries—logging, tracing, auth, rate limiting, caching, argument normalization, or guardrails—without modifying the core flow or wrapping every model and tool individually.

    Callbacks provide declarative Before and After hooks at these boundaries. The framework keeps control of streaming channels, concurrent tool execution, panic recovery, and telemetry; each callback simply inspects the inputs and returns what it wants to adjust, replace, or stop.

    Callbacks vs. Plugins

    • Callbacks are attached to a specific agent (for example via llmagent.WithAgentCallbacks, WithModelCallbacks, or WithToolCallbacks).
    • Plugins bundle callbacks and register them once on a Runner via runner.WithPlugins(...) so they apply globally. At each hook point, plugin callbacks run before agent-local callbacks. See Plugins.

    How Callbacks Work

    Lifecycle

    flowchart TD
    Req["User input enters Runner"] --> BA["BeforeAgent (Plugin -> Agent)"]
    BA -. "CustomResponse" .-> Done["Emit response & finish"]
    BA --> BM["BeforeModel (Plugin -> Agent)"]
    BM -. "CustomResponse" .-> AM["AfterModel (Plugin -> Agent)"]
    BM --> LLM["LLM inference"]
    LLM --> AM
    AM -- "Tool calls" --> BT["BeforeTool (Plugin -> Agent)"]
    BT -. "CustomResult" .-> TRM["ToolResultMessages (optional)"]
    BT --> Tool["Tool execution"]
    Tool --> AT["AfterTool (Plugin -> Agent)"]
    AT --> TRM
    TRM -- "Next turn" --> BM
    AM -- "Final response" --> AA["AfterAgent (Plugin -> Agent)"]
    AA --> TR["AG-UI: BeforeTranslate -> Translate -> AfterTranslate"]

    Dashed arrows show short-circuit paths when a Before* callback returns a non-nil CustomResponse or CustomResult; if AfterTool sets SkipSummarization: true, the turn ends after the tool response instead of looping back to BeforeModel.

    What a Callback Returns

    Every structured callback (Before/After × Agent/Model/Tool) returns (result, error) to express one of four outcomes:

    Outcome Return Value Default Chain Behavior
    Pass through (observe only) nil, nil (or empty &Result{}) Continue to the next callback
    Update context or inputs Non-nil Context, ModifiedArguments, or in-place edits to args.Request Continue and carry the changes forward
    Short-circuit or replace output Non-nil CustomResponse or CustomResult Stop the chain immediately (unless WithContinueOnResponse(true))
    Fail or halt the agent err or agent.NewStopError(...) Stop the chain immediately (unless WithContinueOnError(true))

    Chaining Multiple Callbacks

    All six structured callback chains (BeforeAgent, AfterAgent, BeforeModel, AfterModel, BeforeTool, and AfterTool) share the same execution-control options and result-merging behavior.

    TranslateCallbacks is separate

    TranslateCallbacks (AG-UI event translation) does not merge results across callbacks and has no WithContinueOn* options—it stops on the first error or non-nil custom event. See TranslateCallbacks.

    Execution Control

    Callbacks run in registration order. By default, a chain stops immediately when a callback returns an error or a non-nil CustomResponse/CustomResult. Setting only Context, ModifiedArguments, or SkipSummarization does not stop the chain.

    agent.NewCallbacks, model.NewCallbacks, and tool.NewCallbacks all accept the same two options:

    1
2
3
4
    callbacks := model.NewCallbacks(
    model.WithContinueOnError(true),    // Keep running on errors; return the first error at the end.
    model.WithContinueOnResponse(true), // Keep running on CustomResponse/CustomResult; latest override wins.
)
    Mode ContinueOnError ContinueOnResponse Behavior
    Default false false Stop on the first error or first CustomResponse/CustomResult.
    Continue on Error true false Keep running on errors (preserving the first error); still stop on CustomResponse/CustomResult.
    Continue on Response false true Keep running on overrides (using the last non-nil override); still stop on error.
    Continue on Both true true Run all callbacks; return the merged result alongside the first error (if any).

    When a single callback returns both an error and a custom response/result, error handling runs first (stopping immediately when continueOnError == false).

    How Results Merge Across Callbacks

    In real applications, a callback chain usually combines independent concerns—for example, one callback injects tracing or deadline context, another rewrites tool arguments, and a third logs and returns nothing. Because these callbacks do not know about each other, an unset field in a later result means "leave this alone", not "clear what an earlier callback set".

    Unless execution stops on a callback error, the framework treats each non-nil result as a read-only update and merges it into an accumulator. Returning nil, an empty &Result{}, or a legacy (nil, nil) callback never wipes out earlier fields:

    flowchart LR
    CB1["CB1: {ModifiedArguments: Berlin}"] --> A1["acc = {ModifiedArgs: Berlin}"]
    A1 --> CB2["CB2: {Context: ctxWithTrace}"]
    CB2 --> A2["acc = {ModifiedArgs: Berlin, Context: ctxWithTrace}"]
    A2 --> CB3["CB3: observer / legacy &{}"]
    CB3 --> A3["Final result keeps both ModifiedArgs & Context"]

    Different fields carry different semantics, so merging follows three rules:

    Field Group Fields Merge Rule & Reason
    Independent pipeline state Context (all 6 chains)
    ModifiedArguments (BeforeTool)    		 Latest non-nil wins and is forwarded to subsequent callbacks (ctx / args.Arguments). Each callback can layer onto the previous context or arguments without knowing what other callbacks changed. Derive replacement contexts from the input ctx to preserve cancellation, deadlines, and values; context.Background() or context.WithoutCancel(ctx) deliberately detaches cancellation.
    Result + handling flags CustomResponse (Agent/Model)
    CustomResult + SkipStateDelta (BeforeTool)
    CustomResult + SkipResultFormatter + SkipStateDelta (AfterTool)    		 Replaced together as a unit only when a later callback returns a non-nil CustomResponse or CustomResult. Flags like SkipStateDelta and SkipResultFormatter describe how to handle that specific CustomResult, so they must stay paired with it—under WithContinueOnResponse(true), an empty pass-through keeps the earlier bundle intact, while a new CustomResult replaces both the result and its flags.
    Turn-ending signal SkipSummarization (AfterTool) Logical OR across callbacks (including on early CustomResult stop). Once a callback decides the tool output should end the turn without another LLM call, a later observer that omits the flag should not undo that decision.

    See Behavioral Details & Edge Cases for struct ownership isolation, error-stop return values, and parallel tool publication.

}

type AfterToolResult struct {
    Context             context.Context // Optional replacement context
    CustomResult        any             // If non-nil, replaces the original result
    SkipResultFormatter bool            // Bypass tool result formatter for CustomResult (ignored if CustomResult == nil)
    SkipStateDelta      bool            // Skip tool's state-delta provider for CustomResult (ignored if CustomResult == nil)
    SkipSummarization   bool            // If true, end the turn after tool.response
}

type BeforeToolCallbackStructured func(ctx context.Context, args *tool.BeforeToolArgs) (*tool.BeforeToolResult, error)
type AfterToolCallbackStructured  func(ctx context.Context, args *tool.AfterToolArgs) (*tool.AfterToolResult, error)
    • Modifying arguments: Return BeforeToolResult.ModifiedArguments so tool execution uses the updated JSON (also propagated to TraceToolCall telemetry and graph emitToolStartEvent/emitToolCompleteEvent). Reassigning args.Arguments alone only affects later callbacks in the same chain.
    • Result-handling flags (SkipResultFormatter, SkipStateDelta): Both apply only to a non-nil CustomResult and are ignored when CustomResult == nil:
      • SkipResultFormatter: bypasses the tool's configured result formatter and uses default conversion (model.ToolResultContent stays structured; other values serialize as JSON), useful when returning a protocol or error envelope instead of the tool's declared output type.
      • SkipStateDelta: prevents a non-nil CustomResult from invoking the tool's state-delta provider, useful when the replacement is not a normal tool output.
    • Skipping summarization (SkipSummarization): Ends the turn after tool.response without running an extra summarization LLM call. It does not turn tool.response into a final assistant message; consumers waiting for completion should still read until runner.completion (event.IsRunnerCompletion()).

    Stop Agent via Callbacks

    Return agent.NewStopError from a callback to halt the agent loop cleanly and emit a stop_agent_error event (event.Error.Type == agent.ErrorTypeStopAgentError) to the runner stream—useful for token budgets, guardrails, or manual aborts.

     1

    agentCallbacks := agent.NewCallbacks().
    RegisterBeforeAgent(func(ctx context.Context, args *agent.BeforeAgentArgs) (*agent.BeforeAgentResult, error) {
        if args.Invocation != nil && args.Invocation.TokenUsage.Total >= maxTokens {
            return nil, agent.NewStopError("token limit reached")
        }
        return nil, nil
    }).
    RegisterAfterAgent(func(ctx context.Context, args *agent.AfterAgentArgs) (*agent.AfterAgentResult, error) {
        if args.Error != nil {
            return nil, args.Error
        }
        if args.FullResponseEvent != nil && args.FullResponseEvent.Response != nil &&
            args.FullResponseEvent.Response.Usage.TotalTokens >= maxTokens {
            return nil, agent.NewStopError("token limit reached after response")
        }
        return nil, nil
    })

    Pair agent.NewStopError with context cancellation when you also need a hard cutoff for in-flight model or tool calls (see the Runner docs for cancellation patterns).

    Invocation State: Sharing Data Between Callbacks

    Invocation provides a thread-safe, lazily initialized, invocation-scoped key-value store for sharing data between Before and After callbacks (or middleware):

    1
2
3

func (inv *Invocation) GetState(key string) (any, bool)
func (inv *Invocation) DeleteState(key string)

    Use namespaced keys to avoid collisions, especially when tools run concurrently:

    Scope Key Prefix Convention Example
    Agent callbacks "agent:<key>" "agent:start_time"
    Model callbacks "model:<key>" "model:start_time"

    RegisterAfterTool(func(ctx context.Context, args *tool.AfterToolArgs) (*tool.AfterToolResult, error) {
        toolCallID := args.ToolCallID
        if toolCallID == "" {
            toolCallID = "default"
        }
        key := fmt.Sprintf("tool:%s:%s:start_time", args.ToolName, toolCallID)
        if inv, ok := agent.InvocationFromContext(ctx); ok && inv != nil {
            if startVal, ok := inv.GetState(key); ok {
                fmt.Printf("Tool %s (call %s) took: %v\n", args.ToolName, toolCallID, time.Since(startVal.(time.Time)))
                inv.DeleteState(key) // Clean up to prevent leaks.
            }
        }
        return nil, nil
    })

    All Register* methods return the receiver so you can build reusable callback chains (NewCallbacks().RegisterBefore*(...).RegisterAfter*(...)) and share them across agents—or package them into a Plugin for runner-wide use.

    Behavioral Details & Edge Cases

    The guarantees below apply across all six structured callback chains (Before/After × Agent/Model/Tool):

    • Ownership and mutation isolation: Because Go callbacks return struct pointers, mutating or aliasing those pointers across a chain can corrupt either caller-owned templates or previously accepted fields. Before invoking the next callback, the framework copies accepted top-level fields into its own accumulator and never mutates callback-owned structs (including agent's graph-completion capture preservation). Reusing or clearing a returned struct does not erase accumulated fields; referenced payloads (*model.Response, []byte argument buffers) remain shared rather than deep-copied.
    • Error-stop return boundaries:
      • When continueOnError == false (default): Agent and Model chains return (nil, err); Tool chains return the failing callback's raw (result, err) without merging earlier fields.
      • When continueOnError == true: all six chains return the accumulated result alongside the first error.
    • Parallel tool result publication: In the default merged-result mode for parallel tools, the callback's replacement Context controls tool execution while result publication follows the worker's lifetime—cancelling only the replacement context does not discard a cached result, and detaching cancellation (context.Background() / context.WithoutCancel(ctx)) does not keep publication waiting after the worker is cancelled.
    • Legacy callback signatures: Deprecated non-structured callbacks remain supported via automatic wrappers. Returning (nil, nil) from a legacy callback produces an empty result struct, which acts as a pass-through and preserves earlier accumulated fields (including prior overrides under WithContinueOnResponse(true)).
